## Brief Overview

This rule outlines the principles of context-driven testing, emphasizing that testing practices should be tailored to the specific project context rather than adhering to rigid "best practices."

## Core Principles

- The value of any testing practice depends on its context.
- There are good practices in context, but no universal best practices.
- People working together are the most important part of any project's context.
- Projects unfold unpredictably; testing strategies must adapt.
- The product is a solution; if the problem isn't solved, the product doesn't work.
- Software testing is a challenging intellectual process requiring judgment and skill.
- Testing serves the project and stakeholders, not the other way around.

## Test Creation Approach

- Start with stakeholder needs and project constraints, not standardized templates.
- Define testing objectives based on the specific mission (e.g., development, qualification, debugging).
- Focus on information value—each test's worth lies in its ability to reduce uncertainty.
- Acknowledge that all test oracles are fallible; passing tests don't guarantee correctness.
- Design tests to reveal different types of defects as the program matures.

## Context Considerations

- Identify the project type and its implications (e.g., safety-critical vs. consumer-facing).
- Consider regulatory requirements and their impact on the testing approach.
- Understand the development culture (e.g., engineering precision vs. rapid iteration).
- Account for time-to-market pressures and project timelines.
- Evaluate stakeholder expectations and communication styles.

## Documentation and Artifacts

- Create test documentation that satisfies stakeholders' relevant requirements.
- Avoid standardized documentation templates as starting points.
- Generate artifacts based on project needs, not predetermined standards.
- Ensure documentation serves the project rather than conforming to external standards.

## Metrics and Measurement

- Use only valid metrics that serve the project's specific objectives.
- Avoid metrics that don't provide meaningful information for decision-making.
- Tailor measurement approaches to the project context.

## Testing Strategy Adaptation

- Design different test types for different risk areas.
- Increase test challenge or shift focus as the program stabilizes.
- Adapt the testing approach as the project context changes.
- Choose testing techniques based on the current project phase and stability.

## Stakeholder Service

- Testing exists to provide testing-related services in service of project objectives.
- Test on behalf of stakeholders.
- Balance tester preferences with project needs and constraints.

## Avoiding Anti-Patterns

- Reject context-oblivious testing (copying practices without thought).
- Avoid context-imperial testing (forcing projects to fit standardized practices).
- Don't assume one-size-fits-all approaches work across different projects.
